# 08. 참고 레포 분석: `cindyshin2211/ID-OCR-PROJECT`

마지막 커밋 2024-09-14. 회사 인턴 프로젝트로, README 스스로 "완벽한 기능은 아니고 end-to-end 파이프라인의 기초"라고 밝힌다.

## 1. VLM인가? → 아니다

**YOLOv5(필드 영역 검출) + 필드별 OCR 엔진** 구조다.

```
이미지 → YOLOv5 → [name 박스, id_number 박스, issue_date 박스]
                    ├─ name        → 크롭 → EasyOCR(ko,en)
                    └─ 번호·날짜   → 크롭 → 이진화(threshold 150) → Tesseract(eng)
                  → 정규식으로 문자 정리 → dict
```

앞서 논의한 "bbox 박스치기"가 바로 이 방식이다. 필드 영역 검출기를 학습시키기 위해 labelImg로 75장에 박스를 직접 그렸다
(YOLO 형식 라벨, `data_set/labels/*.txt`).

## 2. 잘한 점

| 항목 | 내용 | 우리 쪽 활용 |
|---|---|---|
| 합성 데이터 파이프라인 | 실물 사진에서 글자를 지워 빈 카드 생성(인페인팅) → StyleGAN2(FFHQ)로 가짜 얼굴 생성 → 가짜 이름·한자·주민번호·주소·발급일·발급기관 합성 | 4단계 합성 데이터 생성기 설계 시 참고 (얼굴 영역은 OCR과 무관하니 회색 박스로 충분) |
| **촬영 조건별 변형 분류** | 파일명 기준 `angle`, `rotated`, `bright`, `filter`, `occluded`, `damaged`, `background`, `near`, `adjust` | **평가셋을 이 축으로 나눠 조건별 정확도를 보는 아이디어는 그대로 채택할 만함** |
| 필드별 다른 OCR | 숫자 필드는 숫자 전용 후처리 | 우리도 필드 형식별 정규화(05 문서)로 같은 효과 |

## 3. 문제점

- **모델 가중치가 레포에 없다** (`yolov5/runs/train/exp/weights/best.pt` 미포함) → `app.py`가 그대로는 실행되지 않음.
- **클래스 이름 불일치로 보임**: `classes.txt`는 `name, id, expiration_date`인데 `app.py`는 `name, id_number, issue_date`를 찾는다.
- 학습 데이터 75장(대부분 같은 템플릿의 변형) → 일반화 검증 없음. 정확도 수치 없음.
- 필드 3개(이름, 주민번호, 날짜)만 추출. 주소·발급기관 없음, 운전면허증 없음.
- GPU/torch + EasyOCR + Tesseract 세 엔진 의존 → 무겁고 CPU 운영에 불리.
- 고정 임계값(150) 이진화 후 Tesseract → 조명 변화에 취약.
- **개인정보 측면에서 따라 하면 안 되는 패턴**: 업로드 파일을 원래 파일명 그대로 `static/uploads/`에 저장(디스크 기록 + 공개 경로 + 파일명 충돌), 추출 결과를 `print`, 예외 메시지를 화면에 그대로 표시, `debug=True`.
- LICENSE 파일 없음 → 코드·데이터 재사용 불가 (특히 실물 기반 인페인팅 배경 이미지).

## 4. 우리 방식과 비교

| | ID-OCR-PROJECT | 우리 |
|---|---|---|
| 필드 위치 찾기 | YOLO 학습 (박스 라벨링 필요) | 범용 텍스트 검출 + 정규식·상대 위치 규칙 (라벨링 불필요) |
| 글자 인식 | EasyOCR + Tesseract | PP-OCRv5 한국어 (ONNX, CPU) |
| 새 필드 추가 | 라벨링 + 재학습 | 규칙 추가 |
| 레이아웃이 크게 다른 문서 | 재학습 필요 | 규칙 추가 |
| 런타임 | torch + GPU 권장 | onnxruntime CPU |

**결론**: 벤치마크 대상은 아님(가중치 없음). **평가셋을 촬영 조건별로 나누는 아이디어**만 4단계에 반영한다.
