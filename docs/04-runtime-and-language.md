## 좋은 코어 vs 많은 코어 (요약)

- 지연시간의 대부분은 검출 모델의 합성곱 연산이고, 클럭과 SIMD(AVX2/AVX-512/VNNI) 성능에 좌우된다.
- onnxruntime의 연산 내부 병렬화는 이 크기 모델에서 보통 4스레드 전후부터 효율이 떨어진다.
- 코어가 많은 쪽이 유리한 건 동시 요청이 많아 처리량이 병목일 때뿐이다.
- 실패 시 재시도 패스(대비 보정, 회전)가 있어서 1회 지연이 짧을수록 최악 지연이 크게 줄어든다.

서버 간 비교는 하지 않지만, Phase 1에서 8코어 서버의 `ORT_INTRA_THREADS`(1/2/3/4) × `OCR_WORKERS`(1/2)
조합만 짧게 측정해 기본값을 정한다. det server vs mobile 모델 지연 차이도 함께 측정.

## Python vs Java (요약)

| 항목 | Python | Java |
|---|---|---|
| OCR 추론 | `rapidocr`가 det/cls/rec와 후처리를 제공 | onnxruntime Java API는 있으나 후처리·디코딩 직접 구현 또는 커뮤니티 포팅 의존 |
| 파인튜닝 | PaddleOCR가 Python 전용 | 불가 → Python 병행 필요 |
| 전처리 일관성 | 학습·서빙이 같은 코드 | 두 언어로 갈라져 정확도 하락 위험 |
| 성능 | 연산은 네이티브(ORT/OpenCV), 연산 중 GIL 해제 | 실질 차이 미미 |

→ 언어 하나, 전처리 코드 하나로 학습·평가·서빙을 모두 처리할 수 있는 Python.
