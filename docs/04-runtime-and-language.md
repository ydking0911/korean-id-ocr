# 04. 운영 서버 선택(좋은 코어 vs 많은 코어)과 개발 언어

## 1. 좋은 코어(8코어/32GB) vs 많은 코어(32코어)

### 워크로드 특성

- 요청 1건 = 검출(det) 1회 + 인식(rec) 텍스트 줄 수만큼 배치. 신분증 1장에서 줄은 20~40개 정도.
- 지연시간 대부분은 **검출 모델의 합성곱 연산**이고, 이건 코어당 성능(클럭, AVX2/AVX-512/VNNI 지원)에 크게 좌우된다.
- onnxruntime의 연산 내부 병렬화(`intra_op_num_threads`)는 이 정도 모델 크기에서 **보통 4스레드 전후부터 효율이 급감**한다.
  (정확한 지점은 Phase 0에서 측정)
- 실패 시 재시도(대비 보정, 90°/270°)가 있어서 최악의 경우 OCR을 3~4번 돈다 → **1회 지연시간이 짧을수록 체감 차이가 크다.**

### 수요 추정

단일 커뮤니티 서버의 가입 인증이므로 동시 요청은 대부분 0~2건이다. 많은 코어가 이기는 상황은
"동시에 수십 건이 몰려 처리량이 병목"일 때인데, 이 서비스는 거기에 해당하지 않는다.

| | 8코어 (좋은 코어) | 32코어 (많은 코어) |
|---|---|---|
| 1건 지연시간 | **유리** (높은 클럭, 단일 스레드 성능) | 서버용 CPU면 클럭이 낮은 경우가 많아 불리할 수 있음 |
| 동시 처리량 | 워커 2개 × 스레드 3~4로 충분 | 워커를 많이 띄울 수 있으나 수요가 없음 |
| 메모리 | 워커당 수백 MB 수준 → 32GB 여유 | 동일 |
| 기타 | 단순 | NUMA 노드가 갈리면 스레드 배치 튜닝 필요 |

**추천: 8코어 서버** (→ DB는 MySQL). 시작 설정 예: `WORKERS=2`, `ORT_THREADS=3`, 남는 코어는 API·디코딩·OS용.

단, 두 서버의 **CPU 모델명**에 따라 결론이 뒤집힐 수 있다 (예: 32코어 쪽이 최신 세대 + AVX-512/VNNI이고 8코어 쪽이 구형인 경우).
Phase 0의 `scripts/bench.py`로 두 서버에서 아래를 측정해 숫자로 결정한다.

```
for threads in 1 2 4 8:        → 1건 지연 p50/p95 (intra_op 스케일링 곡선)
for workers in 1 2 4 (8):      → 초당 처리량, 동시 요청 시 p95
모델: det mobile vs server     → server det가 CPU에서 몇 배 느린지
```

추가로 확인할 만한 최적화: det 입력 크기(`limit_side_len`) 조정, 모델 INT8 양자화(정확도 손실 측정 필요).

### DB 관련

이 레포가 OCR 서비스로 범위가 줄어들면서 **서비스 자체는 DB가 필요 없다.**

- 재시도 제한(10분 3회): 단일 서버·단일 프로세스이므로 메모리로 충분. 컨테이너 재시작 시 초기화되는 정도는 허용 가능.
- 인증 기록: 디스코드 봇 레포의 책임.
- DB가 필요해지는 경우(감사 로그, 다중 인스턴스 재시도 제한)에만 SQLAlchemy로 추상화해 MySQL/Postgres를 설정으로 선택.

## 2. 개발 언어: Python vs Java

### 이 레포에 필요한 것

1. 추론: 전처리 → det → 후처리(DB 박스 계산, 폴리곤 확장) → rec → CTC 디코딩
2. 파인튜닝: PaddleOCR 학습, 합성 데이터 생성, `paddle2onnx` 변환
3. 평가 스크립트, 서비스

### 비교

| 항목 | Python | Java |
|---|---|---|
| OCR 추론 | `rapidocr`가 det/cls/rec와 후처리를 모두 제공. 바로 사용 | onnxruntime Java API는 공식 지원. 하지만 det 후처리(pyclipper/shapely 대체), CTC 디코딩, 전처리를 직접 구현하거나 커뮤니티 포팅(RapidOcr-Java 등, 유지보수 상태 확인 필요)에 의존 |
| 파인튜닝 | PaddleOCR 자체가 Python. 필수 | 불가능 → **결국 Python 병행** |
| 전처리 일관성 | 학습·서빙이 같은 코드 | 학습(Python)과 서빙(Java)의 전처리가 갈라져 정확도 하락 위험 |
| 동시성 | GIL이 있지만 onnxruntime/OpenCV가 연산 중 GIL을 놓아 스레드풀로 병렬 처리 가능 | 진짜 멀티스레드. 다만 병목이 네이티브 ORT라 실질 이득 작음 |
| 성능 | 연산은 네이티브(ORT/OpenCV)에서 수행 → 언어 차이 미미 | 동일 |
| 메모리/배포 | 이미지 수백 MB (opencv, numpy) | JVM + ORT 네이티브 라이브러리, 비슷하거나 더 큼 |
| 개인정보 | `bytes` 덮어쓰기 불가 | `byte[]`는 `Arrays.fill`로 0 덮어쓰기 가능 (단, GC 복사본은 통제 불가) — 소폭 우위 |
| 팀/인프라 친화성 | | 사내 표준이 Spring/Java라면 운영·모니터링이 익숙함 |

### 추천: Python

- 파인튜닝 때문에 Python은 어차피 필요하고, 추론까지 Python으로 하면 **언어 하나 + 전처리 코드 하나**로 끝난다.
- 연산은 네이티브에서 돌기 때문에 Java로 바꿔도 성능 이득이 거의 없다.
- 서비스 경계가 HTTP라서 호출 쪽(디스코드 봇이나 다른 시스템)은 어떤 언어로 써도 상관없다.

Java가 의미 있는 경우: 사내 운영 표준이 JVM이라 Python 컨테이너 운영 자체가 부담일 때. 그때도 **학습·평가는 Python, 서빙만 Java**로
분리하고, 전처리 일치 여부를 검증하는 교차 테스트(같은 입력 → 같은 텐서)가 필요해진다.
