# 07. 참고 레포 분석: `junhyeoksin/ocr-ai-module`

마지막 커밋 2025-06-21. Python ~1,800줄.

## 1. README 주장 vs 실제 코드

| README | 실제 |
|---|---|
| "고성능 OCR AI 모듈", "딥러닝 기반 OCR 시스템" | **OCR 코드가 없다.** `easyocr`, `pytesseract`, `torch`, `ultralytics`는 requirements에만 있고 import하는 곳이 없음. README도 "YOLO + CRNN 기반 OCR 모델"을 향후 계획으로 적어 둠 |
| "지능형 기울기 보정" | Canny + HoughLines로 각도 추정 후 회전. 함수명은 `correct_perspective`지만 **원근 보정은 아님** |
| "고품질 인페인팅 템플릿" | 주민등록증 이미지에서 글자를 지워 빈 템플릿을 만드는 기능. 결과물 `app/dataset/idcard_template.png`에는 **글자가 그대로 남아 있고 인페인팅 아티팩트가 심함** → 합성 배경으로 쓰기 어려움 |
| "합성 데이터 + YOLO/COCO 어노테이션" | 고정 좌표에 Faker 텍스트를 그림. 실물에 없는 `birth_date` 필드가 따로 있는 등 **실물 레이아웃과 다름** |
| MIT 라이선스 배지 | **LICENSE 파일 없음** → 법적으로는 재사용 허락이 없는 상태 |
| 벤치마크 수치 | 전처리(OpenCV)만의 속도. OCR 정확도 수치 없음 |

## 2. 쓸 만한 아이디어 (코드는 가져오지 않고 개념만)

| 아이디어 | 우리 쪽 적용 |
|---|---|
| 라플라시안 분산(선명도), 밝기, 대비 측정 | OCR 전에 **품질 사전 검사** → 너무 흐리거나 어두우면 OCR을 돌리지 않고 `fail_reason: IMAGE_TOO_BLURRY / TOO_DARK` 반환. CPU 절약 + 클라이언트에 구체적인 재촬영 안내 |
| CLAHE 대비 강화 | 이미 계획에 있음 (실패 시 재시도 패스) |
| 빈 카드 템플릿 위에 텍스트 합성 | 방향은 맞음. 다만 인페인팅 대신 **빈 배경을 직접 그리거나 SAMPLE 견본 이미지를 깨끗하게 재작업**하는 쪽이 품질이 낫다 |

## 3. 따라 하면 안 되는 것

- **딥러닝 OCR 전에 적응형 이진화를 적용하는 것.** PP-OCR 같은 모델은 컬러/그레이 이미지로 학습되어 있어서
  이진화하면 오히려 정확도가 떨어지는 경우가 많다. 우리 파이프라인에서는 이진화를 쓰지 않는다.
- 고정 800×500 리사이즈 (종횡비 왜곡). 우리는 긴 변 기준 비율 유지 리사이즈.
- 모든 단계마다 `logger.info`로 경로·크기 출력 → 무해해 보여도 로그 습관상 개인정보 원칙과 맞지 않음.

## 4. 벤치마크 대상인가?

**아니다.** 인식 모델이 없어서 비교할 대상 자체가 없다. 06 문서의 `ai-ocr-finetuning`(Donut)만 기준선 비교 대상으로 유지.
