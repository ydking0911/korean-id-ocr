# 03. 결정 사항 및 남은 질문

상태: 🟡 논의 중 / ✅ 결정됨 / ⛔ 범위 밖

## 결정 로그

| 주제 | 상태 | 결정 |
|---|---|---|
| 범위 | ✅ | **① CPU OCR worker Docker 기동 → ② 신분증 OCR → 구조화 JSON.** 모델 구성에만 집중 |
| 성인 판정 | ⛔ | 하지 않음. 파생 필드 `birth_date`만 제공 (05 문서) |
| 디스코드 봇 / 제출 방식 / 유저 재시도 제한 | ⛔ | 호출 측 |
| DB (MySQL 포함) | ⛔ | 출력 JSON만 잘 나오면 됨. 현 시점 계획 밖 |
| 호출 서비스 연동 | ⛔ | 같은 호스트의 Docker 밖에서 호출 예정. 네트워크·인증 구성은 범위 밖 |
| 전처리 | ✅ | EXIF 회전 보정·리사이즈 **항상**, 대비 보정·90°/270° 회전은 **실패 시에만** (내부 재시도 패스) |
| 운영 서버 | ✅ | 8코어/32GB (최신 세대). 서버 간 벤치마크 생략 |
| 언어 | ✅ | Python |
| 실물 검증 | ✅ | 본인 신분증 가림 상태로 로컬에서만. 저장소에 포함 안 함 |
| 주민번호 출력 | ✅ | 개발용이라 **전체 출력**. 마스킹은 설정 키만 준비 (05 문서 5절). 로그·예외에는 남기지 않음 |
| 지원 문서 | ✅ | 주민등록증·운전면허증 **앞면만**. 뒷면·모바일 신분증 제외 |
| `/v1/ocr/raw` | ✅ | 개발에서만 켜고 운영에선 설정으로 끔 |
| 파인튜닝 | ✅ | **기본 계획에서 제외.** 평가 하네스로 실패 원인을 본 뒤 인식 모델의 일관된 오인식이 주원인일 때만 (06 문서 3절) |
| 참고 레포 벤치마크 | ✅ | 우선순위 낮음(선택). `ocr-ai-module`은 OCR 모델이 없어 대상 아님 (07 문서) |
| 구조화 스키마 | 🟡 | 05 문서 추천안 v1 — 검토 필요 |
| 이미지 품질 사전 검사 | 🟡 | 선명도·밝기 기준 미달이면 OCR 생략하고 `IMAGE_TOO_BLURRY` 등 반환 (07 문서) |

## 남은 질문

### Q1. 구조화 스키마 검토 (05 문서)
필드 목록·키 이름·정규화 형식(날짜 `YYYY-MM-DD` 등)이 원하는 형태인지. 특히:
- 실패 필드를 `null`로 두고 키는 유지하는 방식
- `field_meta`(신뢰도·bbox·검증 결과)를 기본 응답에 포함할지

### Q2. 이미지 품질 사전 검사
흐린 사진을 OCR 전에 거부할지, 일단 OCR을 돌리고 결과로만 판단할지.
추천: 사전 검사는 **경고만**(`warnings: ["BLURRY"]`) 내고 OCR은 진행 → 임계값을 데이터로 정한 뒤 거부로 전환.

### Q3. 모델 파일 확인 (01 문서 2절)
개발 PC에서 `monkt/paddleocr-onnx` 파일 목록 확인 필요 (이 작업 환경은 HF 차단).
- `det.onnx` ~84MB가 server 모델인지 → CPU 지연에 영향. mobile det도 같이 받아 비교 추천
- RapidOCR 공식 배포(`korean_PP-OCRv5_rec_mobile`)와 같은 모델인지
- 한국어 dict에 성명 한자가 얼마나 들어 있는지 (한자 성명 인식 가능 여부)
