# 06. 파인튜닝 — 참고 레포 분석과 계획

## 1. `wonby1n/ai-ocr-finetuning`은 어떻게 했나

| 항목 | 내용 |
|---|---|
| 접근 방식 | **OCR 엔진이 아닌 문서 이해(VLM) 모델**을 파인튜닝해서 이미지 → JSON을 한 번에 생성. Donut(200M) 또는 Qwen2.5-VL + QLoRA |
| 대상 문서 | 운전면허증, 여권. **주민등록증 없음** |
| 데이터 | Faker + PIL로 만든 합성 이미지 기본 500장(문서 종류별). 단일 고정 레이아웃(파란 헤더 바, "KOR" 박스 등), 가우시안 노이즈, ±2° 회전만 |
| 분할 | 같은 생성기 출력을 train/val/test 80/10/10으로 분할 |
| 평가 | 필드별 **완전 일치** 정확도, 완벽 일치 비율 (`scripts/inference/evaluate.py`) |
| 서빙 | `pytorch/pytorch:…cuda12.1` 이미지, FastAPI, GPU 전제, `--workers 1` |
| 결과물 | HF Hub `wonby1n/korean-ocr-donut` (README 기준. 이 환경에선 HF 차단으로 미확인) |

### 문제점

1. **평가가 실제 성능을 말해주지 않는다.** 테스트셋이 학습과 같은 생성기·같은 레이아웃에서 나와서, 높은 점수는 "템플릿 암기"일 수 있다.
   실촬영 사진 평가가 전혀 없다.
2. **합성 레이아웃이 실물과 다르다.** 실제 운전면허증의 필드 배치·서체·배경 무늬(홀로그램, 길로셰)·색과 다르고,
   원근 왜곡·조명·반사·흐림·배경(책상, 손) 같은 촬영 노이즈가 없다.
3. **운영 제약과 맞지 않는다.** torch + transformers + GPU 전제. CPU에서 Donut은 장당 수 초, 2B급 VLM은 훨씬 느리다.
   우리 런타임 제약(CPU, PyTorch 없음)과 정면으로 충돌.
4. **설정 오류 의심**: `Qwen/Qwen2.5-VL-2B-Instruct`를 기본 모델로 쓰는데, Qwen2.5-VL 공식 라인업은 3B/7B/32B/72B로 알고 있고
   2B는 Qwen2-VL에만 있다 (HF 차단으로 직접 확인은 못 함). `upload_to_hub.py`도 `Qwen2VLForConditionalGeneration` 클래스를 쓴다.
5. **라이선스 파일이 없다** → 코드를 그대로 가져다 쓸 수 없다 (저작권자 허락 필요). 아이디어 참고만.

## 2. 벤치마크해도 되나?

**된다. 단, "비교 기준선"으로만.**

- 우리 `eval/` 하네스에 어댑터를 하나 추가해서, 같은 평가셋에 대해 **우리 파이프라인 vs 그 레포의 Donut 모델**을 비교.
- 실행은 개발 PC(RTX 3070)의 **별도 가상환경**(`eval/baselines/`, `requirements-baseline.txt`)에서만. 서빙 이미지·의존성에는 절대 넣지 않음.
- 비교 지표: 필드별 정확도(완전 일치 + 문자 오류율 CER), 장당 지연시간(CPU/GPU), 메모리.
- 운전면허증만 비교 가능 (그 모델은 주민등록증 미학습).
- Qwen 쪽은 공개된 가중치가 없어서(LoRA를 직접 학습해야 함) 제외.
- 그쪽 HF 모델의 라이선스도 확인 필요. 평가 목적의 로컬 실행만 하고 재배포하지 않는다.

예상: 우리 합성 평가셋에서는 비슷하거나 그쪽이 높게 나올 수 있지만(문서 레이아웃이 달라 오히려 낮을 수도),
**실촬영 평가셋에서의 격차**가 판단 기준이다.

## 3. 우리 파인튜닝 방침

### 왜 VLM이 아니라 OCR(det+rec) + 규칙 기반 구조화인가

| | OCR + 레이아웃 규칙 (우리) | 엔드투엔드 VLM (참고 레포) |
|---|---|---|
| CPU 추론 | 수백 ms 수준 기대 | 수 초 이상 |
| 실패 원인 추적 | 검출/인식/규칙 중 어디서 틀렸는지 분리됨 | 블랙박스 |
| 환각 | 없음 (읽은 글자만 반환) | 그럴듯한 가짜 값 생성 위험 — 신분증에 치명적 |
| 신규 문서 추가 | 규칙 추가 | 재학습 |
| 레이아웃이 매우 다양할 때 | 약함 | 강함 |

신분증은 레이아웃이 고정된 문서라 규칙 기반이 잘 맞는다.

### 무엇을 파인튜닝하나

1. **먼저 기본 모델로 오류 분석** — 틀린 필드가 검출 누락인지, 인식 오류인지, 구조화 규칙 문제인지 분류.
2. 인식 오류가 주원인이면 **인식(rec) 모델 파인튜닝** (PP-OCRv5 korean rec, PaddleOCR):
   - 학습 단위는 카드 전체가 아니라 **텍스트 줄 크롭** (이름, 주민번호, 주소, 날짜, 면허번호 등)
   - 신분증 서체와 비슷한 폰트, 숫자·하이픈·마침표 비중 높임, 실제 주소 체계(행정구역명) 사전 사용
3. 검출 누락이 주원인일 때만 det 파인튜닝 (카드 전체 합성 이미지 + 박스 라벨 필요 → 비용 큼).
4. 변환: Paddle 학습 → inference 모델 export → `paddle2onnx` → ONNX를 RapidOCR에 경로로 지정.
5. 학습 환경: 개발 PC 전용 Docker 이미지(`training/Dockerfile`, PaddlePaddle GPU). **서빙 이미지와 완전히 분리.**

### 데이터 (참고 레포의 실수를 반복하지 않기)

| 원칙 | 방법 |
|---|---|
| 실물에 가까운 레이아웃 | 실물 필드 위치·서체 크기 비율을 본인 카드로 측정해 템플릿화 (사진·번호는 가짜) |
| 촬영 노이즈 | 원근 변환, 조명 그라데이션, 반사 하이라이트, 모션/초점 블러, JPEG 재압축, 배경 합성 |
| 인쇄→재촬영 | 합성 카드를 출력하거나 모니터에 띄워 폰으로 촬영한 샘플을 섞음 |
| 평가 분리 | **합성 평가셋은 학습과 다른 시드·다른 배경·다른 노이즈 파라미터**로 생성 |
| 실촬영 평가 | 본인 신분증(가림) 소량, 로컬 전용. 개선 여부의 최종 판단 기준 |
| 공개 데이터 | AI Hub "공공행정문서 OCR", "한국어 글자체 이미지" 등을 rec 사전 보강에 검토 (이용 약관 확인) |

### 평가 지표

- 필드별 완전 일치율, 문자 오류율(CER)
- 문서 단위: 필수 필드 전부 정답인 비율
- `status` 보정: 틀린 값을 `OK`로 내보낸 비율(가장 나쁜 오류)을 따로 집계 → confidence 임계값 조정에 사용
